### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут с использованием web сервиса компании контролировать сенсоры (включать/выключать), которые отвечают за отопление в их домах.
- Система позволяет удаленно управлять установленными в домах реле, отвечающие за включение и выключение сенсоров.
- Специалисты системы  подключают новые сенсоры и добовляют к текущей версии системы.

**Мониторинг температуры:**

- Пользователи могут при необходимости удалённо узнать температуру в своих домах.
- Система выступает в роли "УСПД (Устройство сбора и передачи данных)", а имеено собирает показания температуры с сенсоров.
- Система ведет учет подключенных сенсоров.

### 2. Анализ архитектуры монолитного приложения

**Язык программирования:** Go
**База данных:** PostgreSQL
**Архитектура:** Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
**Взаимодействие:** Синхронное, запросы обрабатываются последовательно.
**Масштабируемость:** Ограничена, так как монолит сложно масштабировать по частям.
**Развертывание:** Требует остановки всего приложения.

### **4. Проблемы монолитного решения**

- **Высокий риск ошибок и задержки** связанный с внесением новых изменений, потому что над проектом монолитного приложения теперь работает команда из 5 программистов.
- **Увеличивается время** на осознание/cоглассованности добавления нового/изменения существующего функционала в монолитном приложении командой разработки.
- **Замедляется выпуск новой версии** продукта из-за увеличения времени тестирования монолитного приложения после добавления нового/изменения существующего функционала командой QA перед выкладкой в продакшан.
- Перед выкладкой новой версии в продакшан необходимо **остановить полностью весь монолит**, что в свою очередь может привести к репутационным издержкам.
- Монолитное приложение **сложно масштабировать** в моменте для динамически неизвестной нагрузки на проект в продашане, нужно делать полную копию что приводит к увеличению ресурсов для поддержания работоспособности.
- **Уход ключевого программиста** может повлиять на рост сложности обслуживания системы после его ухода, потому что новым программистам понадобится много времени на знакомство с проектом.

Все выше перечисленные проблемы **приводят к тормажению развития бизнеса/компании**

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql
